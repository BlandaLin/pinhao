# 让不会编码的 AI 专心做好汉化文字工作

不必让同一个 AI 既理解引擎二进制、维护映射，又翻译整部游戏。先由技术人员把游戏文本组织成可编辑工作表，再让文字 AI 只处理文字。这样，模型换了、会话断了、翻译分批了，都不必重新拆包和猜上下文。

## 工作台要交付什么

一条文本单元包含稳定 ID、完整原文、译文栏、说话人/位置/分支和控制符占位符。技术映射留在后台，记录它该写回哪些文件、命令或原生翻译 ID。文字 AI 不必看懂这些映射，也不允许改它们。

例如一个两行对话窗，阅读参照是：

```text
Hello, \N[1].
Come this way.
```

工作表把它作为**一条**完整对话，不切成两个脱离上下文的碎片：

```json
{
  "source": "Hello, {{CTRL0001}}.{{LINE0001}}Come this way.",
  "translation": "您好，{{CTRL0001}}。{{LINE0001}}请这边走。"
}
```

这是字段示意，不是可直接提交的完整记录。回包必须保留真实工作表里的 ID 等全部字段。动态人名、等待、颜色、分行交由程序还原，文字 AI 不需要手写引擎语法。

## 完整上下文不是无限长上下文

按原有消息窗或段落组织单元，按文件/场景切批；需要跨窗理解时，附只读前后文。互斥选项分支保持分开，不能为“连贯”拼成同一条剧情。原文相同也可能语境不同，稳定 ID 不能只是原文字符串的哈希。

被旧工具切碎的译文应回到原始事件结构重新提取，再把能确认的成果映射回来。仅凭标点或相似字符串拼接，很容易错序和串分支。原版资源不足时，标明无法恢复的部分，不让 AI 猜完就装回。

## 三类文字任务顺序交接

先初翻，用术语表确定人名和称呼；再校对原意、关系、人称与动作主客体；最后润色中文。后一阶段读取前一阶段的有效完整工作表。每阶段可保存一个版本，不能把各阶段重复 ID 的补丁堆到一起，指望程序自动挑出“最新最好”的句子。

文字 AI 只需改 translation 与 notes，返回完整文件集合。它不负责计算基线 hash、不维护编译脚本，也不需要声称程序通过。模型无法判断的语义问题，留在 notes 里交接；文件少、职责明确，比反复附上所有聊天历史更省工时。

## 技术侧做机器擅长的检查

校验文件与记录是否完整、ID/source/context 是否变动、占位符是否丢失或重排、回包是否用错基线。未知 ID、重复 ID 和语法注入拒绝处理，不按文件名顺序静默覆盖。用稳定映射回写，并证明非文本事件/分支/数值没变。

“格式正确”和“译得正确”不同。比如把男性人物写成“她”，通常完全符合 JSON 和占位符规则；程序不该因此宣称质量通过。文字校对要依据原文和角色资料作判断。

## 先花小钱证明路线

先跑原样提取/回写，要求未修改数据字节一致。再选一个短场景、一个选择分支和一个数据库说明做闭环。字节校验成功后还要在真实引擎中检查显示、操作、保存和载入。小样不过就不要全量翻译，避免把大量 Token 花在一个装不回去的路线。

本包的三个中性示例会帮你练习文件流程，不需要准备游戏。它们不含引擎运行器，因此只能证明数据流程，不证明商业游戏可启动。

## 发布前仍需技术验收

文字表翻完，不等于图片、JS UI、字体图集或旧存档名字自动完成。姓名框、菜单、长选项、缺字、回想房、道具描述都要另测。旧存档只迁移确认过的默认文字值，保留自定义名字和进度，不全局替换所有字符串。

分享时从干净副本打包，排除个人存档、日志、缓存、私有路径与密钥，保留运行依赖和字体许可。公开教程不需要附商业游戏或个人通关档。

节省的具体工时取决于项目，但这套办法能把反复查 ID、数控制符、猜回写位置和接续会话的工作从文字 AI 身上移走。提示词不是能力保证；真正可靠的是职责分离、完整上下文和能复现的校验流程。
