# 给真实项目建立低编码负担的文字工作包

本规范定义职责与交付，不强制不同引擎采用相同物理文件。toolkit 的 schema 是已有可用实现；未知引擎可以适配，但先证明格式和小样闭环。

## 最少六种对象

| 对象 | 用途 | 谁能修改 |
| --- | --- | --- |
| 原版资源 | 恢复与独立复核依据 | 本项目保持只读 |
| baseline 和 manifest | 固定输入身份、源资源哈希、文本目标映射 | 提取后保持只读 |
| editable | 稳定单元、整段原文、上下文、译文、备注 | 文字 AI 只改 translation/notes |
| 术语与角色证据 | 统一称谓、消除人称猜测 | 负责人定稿，文字 AI 可提建议 |
| 批次台账 | 当前有效版本、已交/已回/未处理范围 | 技术 AI 或负责人 |
| 验收报告 | 数据闭环、原生导入、实机范围和缺口 | 按实际证据填写 |

toolkit 的 editable 每条现有字段必须原样保留。新增人物资料、场景摘要或前后参照可用 companion 文件按 ID 引用；不要修改只读表结构后再期待旧校验器接受。

## 稳定 ID 与映射

ID 要绑定逻辑单元和原生位置，不仅绑定原文。重复原文分别保留，能确认是共享名字/同一原生字符串时才共享映射。选择项若有显示和分支标签两处，一条记录映射两处同步回写；不能让文字 AI 自行找全部引用。

提取器版本、源资源和规则不变时，应可重复生成同样 ID/顺序。重新提取不同版本会改变 ID 时，应报告差异并显式迁移，不能把旧回包装进新 manifest。固定基线 hash 由技术侧计算并预填，文字人员不管理它。

## 完整单元与上下文

以消息窗/段落/原生翻译条目为边界，不按任意字符数切句。长单元先按引擎实际显示规则定位，不为了 API 请求大小随意拆成可回写碎片。批次只在单元之间切，优先按文件/场景组织。

至少保留说话人未知状态、原生位置、分支、只读原文参照。未确认的性别写 unknown；有角色 ID/原文设定证据再记录。不要把头像、职业或名字当证据。更多前后文按批次提供，不反复发送全项目历史。

## 控制符与纯文字回包

保护动态人名、颜色、等待、换行、格式参数、标签和链接目标为占位符，记录准确还原映射。引擎差异很大，不把本包一个正则称为通用规则；遇到新语法先加中性测试。

如果文字 AI 不善于 JSON，可按本包 `text-only-ai` 的方式只给 ID/TEXT/NOTE：文件头与 hash 已填好，ID 只读，译文与备注可填。原文/context 留在 READING.md。技术程序根据固定顺序与完整 ID 集合复原工作表，再走同一校验器。

本包 from-text 是中性 lesson 的入口；真实 work 用 export-text/import-text，直接兼容本包 toolkit 的工作表与校验器，不用另写转换器。未知旧格式需明确适配，不能从模糊聊天段落猜 ID。普通完整 editable 已能用时，不必强制多加一层。

## 版本链别丢译文

初翻、校对、润色各自保存一个完整有效版本。增量补丁必须写明以何版本为父输入。toolkit merge 以原始基线为底，重复 ID 拒绝处理；它没有“自动承接前一补丁”的能力。

因此推荐文字侧完整表串行交接。需要最终增量交付时，技术侧从当前有效完整表与原始基线比较，生成全部最终差量：一 ID 只有一个终值。多个版本的覆盖由负责人明确裁决，不按文件名、时间或最后写入静默选择。

## 校验到发布

先原样回写字节一致，再单场景小样，后全量。完整表先 validate，增量先 merge，然后 build/verify。记录 changed 数，不用“单元数多”当翻译完成率。不同适配器的 verify 是数据证据，不是运行证据。

build 只是一组基线资源/源文件，不等于完整游戏；桥接格式还需原生导入。测试副本验收字体、长选项、控制符、人名、存档、回想房与 UI。图片文字、代码内 UI 和旧档值单独列未处理项。

完成后从干净目录打分享包，检查解压副本，不带个人存档与凭据。测试报告分别写结构校验、语义校对、原生导入、启动、旧档、完整试玩的状态；未执行就是未执行。
