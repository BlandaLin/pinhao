# 文字执行与成果接力

拼好汉化把文字提取、语义准备、翻译、校对和独立成品接成一条制作链。
Agent 负责理解人物、义项和场景，主程序负责保存证据、安排任务、核对修订并写回游戏。
用户配置 API、导入游戏后即可开始制作，也可以通过文字工作包交给自己的工具处理。

## 六组工作如何衔接

| 环节 | 当前实现 |
| --- | --- |
| 成果接受与恢复 | 正常回复、流式完整记录和保存候选共用接受规则；关联字段、修订和证据一起核对 |
| 技术工具与适配 | 完整工具证据、分页补读、原生工具、隔离配方、小样验证和失败返修接入制作流程 |
| 资源覆盖 | 显示位置、未知字段簇和已有定位分别记录；已验证文字可以继续制作 |
| 语义准备与复用 | 按需补查原文，保存有范围和证据的语义决定；明确授权的等义关系可以复用译文 |
| 差分校对 | 明确确认本批审完，只提交必要改文和具体疑点 |
| 独立成品与证明 | 最终文件清单绑定成品内容；原生检查、启动观察和实际游玩各自记录 |

技术适配的工具与执行细节见 [技术 Agent 自主适配](AUTONOMOUS_ADAPTATION.md)。

## 1. 先保留完整文字，再组织请求

提取结果以完整语义单元保存。每个单元都有稳定 ID、源文、类型、上下文和准确回写定位。
控制符、人物引用和资源标记随单元一起保存；同一 `syncGroup` 的关联显示字段整组处理。

主程序保存完整场景和人物范围，再按请求大小组织运输批次；同一范围可以包含多次请求。
同场景的对白、公共事件及有明确依据的人物资料提供版本化阅读入口。长材料按页读取，
每页保留实际 ID、版本及阅读位置。完整单元和关联组保持完整，较长单元单独发送。

同一轮先完成翻译，再完成场景校对。程序复用独立出处的译名投票和场景成果；只有仍有
实际译名分歧或明确疑点的文字才交给模型定向复核，不再自动追加一轮全量校对。翻译和校对各阶段内继续共用
全局并发池。初翻不再等待预先整理整张术语表；已确认译名作为相关参考，不阻断正文。
局部失败保留当前文字。有有效成果的任务在有限补交后，将仍未通过的文字明确列为待重试，
其余独立任务继续；普通暂停续跑不会再次购买这些问题文字，可用“重试问题文字”主动处理。
整批始终没有有效交稿、接口或存储故障等阻塞仍会暂停；用户明确启用局部失败即暂停时同样暂停。
已保存的有效成果不清空，未完成校对的文字不标为校对完成。

内置 API 使用 `pinhao-text-blocks-3` 分段协议：请求正文按完整文字块呈现，使用 `u1`、`u2`
等短标记，附必要的现译、人物、术语和场景语境。稳定 ID、资源定位、摘要和修订号留在主程序，
不要求模型复制工程结构。普通翻译返回纯文字：

```text
[u1]
欢迎回来。
[u2]
谢谢。
[完成]
```

正文不需要 JSON 引号、逗号或空备注。程序按任务保存的短标记表恢复原定位，
不按返回行数拼接；未知、重复或只读参考标记不能成为写入目标。行首准确短标记与正文同行
（例如 `[u1] 译文`）也可识别，裸 `u1` 不能据此猜成编号。原文、现译或备注若含同形标记行，
请求会改用双层或更深括号；输入碰撞检查与回复解析共用同一标记规则。
明确下一标记前的空白分隔行属于协议排版，不写入译文；正文内部段落、缩进和行尾空格保留。
没有后续标记的正常裸 EOF 只去掉一次终止换行，中断不关闭未完成尾块。可识别包住整个回复
的一层 text/plaintext 代码围栏或开头 BOM，但围栏不能让中断尾块冒充完成。原文中的保护标记
及顺序必须保留；若原文换行已编码为保护标记，则用该标记返回，不新增裸换行。

交稿要求集中在请求的“交稿方式”区：目标标记、正文、完成标记共同构成交稿，
不能将“不写解释”理解成省略标记。补交按实际未通过目标及逐项原因生成，
明确所缺标记和必须保留的控制标记顺序，不重复无关的备注、译名与决定教程。
必要的原文、语境、资料入口和按需补查能力仍保留；不以猜编号接收无标记正文。
不再用真实目标编号演示一份可被误抄的交稿。
校对没有修改时仅返回完成标记；若存在非空未编号前言或外壳后尾注，不能据此确认整批已审完。
准确闭合且通过检查的改文仍按原有部分成果机制保留，其余文字不冒充已审阅。
响应先完整接收并保存现有正文、结束原因和可取得的用量，再在同一次响应的终态统一验收；
格式问题不提前终止接收。单一明确交稿前的未标记前言不作为译文，只有前言仍不算交付。
重复编号、第二交稿区与只读编号不会按最后一份覆盖；可定位的独立有效条目仍需经过原有校验。
断流、取消或截断时只保留明确闭合的块，不把未闭合末句或未完成校对当作正常结束。

初翻可在完成标记后以独立的 `[附加信息]` 行附一个 JSON 对象，其中
`terms:[["u1","原文中出现的专名或术语","本句实际采用的译名"]]` 记录实际译名。
`remarks:[["u1","本条说明"]]` 只附给本次实际交付的正文，不要求空项；它与累积阅读笔记 `notes` 不同。
普通正文不需要填写这些附加资料。附加资料错误时保留有效正文并记录具体问题。
缺少或无效的译名对应不导致有效正文丢失、补交或重新调用。正式接受译文时一起保存对应记录。
初翻结束后在本地扫描已接受的对应及结构化姓名字段，去除重复原文、关联显示与自动分发副本后计票。
只有身份明确且严格过半的名字可自动更新整字段；人工锁优先，程序不全局替换对白子串。
自动改写保留原始票源，不把程序的改写重新算作模型投票。
实际存在分歧时，已有校对请求只附本批相关的原词、候选译名、票数和短标记，不复制整套语境。
校对正式提交后记录其所核对的译名分歧；相关原文、译文或候选变化会使确认失效。
校对沿用文字模型连接，不再要求单独配置校对接口；工程定位与最终组装继续由软件负责。

短标记表随任务保存，分页、暂停和重启后继续使用同一含义。初译不重复发送与原文相同的现译；
真实已有译文和人工备注继续提供。控制符与关联显示约束仍由主程序核对，最终游戏由软件组装。

同批重复的语境字段只保存一份共享说明，每条保留适用引用和独有条件；不同说话人、分支和
义项不因此合并。译名候选只附相关译法、独立票数、作用域及补查入口，不重复发送全部出处编号。
本地仍保留完整证据和修订依赖。固定交稿规则及共用材料排在变化正文之前，便于服务商复用
相同前缀；每次仍发送完整必要材料，不依赖模型记忆，也不保证服务商缓存命中。

分批以完整语义单元及关联组为单位，复用当前快照的文字投影和场景、人物、分支位置索引。
先累计材料成本选择候选批次，再组装完整实际请求并统一估算输入与输出；不为每添加一个单元
重建整份消息。轻量成本只用于组织候选，不能单独认定容量不足。完整请求超限时退回完整组
重新安排，只有不可再分的完整组仍超限才报告容量问题；不假设可选语境裁剪后的批次大小单调。

容量是模型的处理上限，不是每次必须填满的目标。初翻按全部译文估算输出，校对同时考虑
现译和整批修改所需空间，并保留推理余量。不从历史总输出用量反推每条译文的大小，也不把
推理等固定开销逐条摊成会不断缩批的反馈。执行批次复用容量检查时组装的正文与语境；补查或
修复改变消息后重新检查。真实截断可只缩小未完成部分，不清空已接受文字。

调度器按批次逐步入队并立即启动可运行任务，不等待整个队列窗口准备完毕。规划在批次之间
让出执行时间，及时处理进度、暂停和取消；有界前瞻只限制提前准备的任务数量，不降低配置的
独立并发。规划期间资料或运行状态变化时停止使用旧快照，按现有修订与恢复机制继续。

这种共享首先减少请求中的重复编码。实际请求数、耗时与供应商返回的 usage 分别记录，
成本和质量对照以同模型、同材料的实测结果为准。

## 2. Agent 按需补查语义证据

翻译与校对通过 `read` 返回查询，按原文、短标记、文字类型或场景人物入口查询项目已有文字。
需要先补查时，只返回 `[附加信息]` 及查询 JSON，不同时交正文或声称本批完成。
查询支持分页，主程序提供匹配原文、匹配总数、下一页位置和只读标记。
零结果查询也保存回执，后续新增相关文字时可以重新判断旧决定。
`read:[{term:"原词"}]` 按术语的规范化和词边界规则查询全部出现位置，支持全角/半角形式；
`text` 仍按原文字面子串匹配。查询只提供证据，不把同词出现自动认定为同一人物或义项。

单次回复最多提出两项查询。普通场景和人物分页阅读独立记录进展，继续读取后续页面；
语义疑点的失败补查使用有限轮次，达到上限时保存明确的待补证据记录。
Agent 在 `notes` 中保存带短标记的累积阅读笔记，用于接续后页阅读和按标记回查。

Agent 可以在翻译回复的 `decisions` 中发布有复用价值的语义决定。每项决定包含：

- `ref`（修订已有决定时）：主程序提供的短标记。
- `entity` 与 `sense`：具体对象及其在当前场景中的义项。
- `scope.unitIds`：适用文字的短标记。
- `evidenceIds`：实际读过的文字短标记。
- `translation`（可选）：确认的目标表达。

决定的稳定编号和本次依据的修订由主程序绑定，模型不生成工程身份或猜测版本。

主程序保存决定历史和读集，并核对当前原文、上下文、现译、备注及相关术语。
证据、查询结果或决定修订变化时，相关旧任务按最新资料重新安排；其他有效任务继续复用成果。

## 3. 译文复用由明确的语义决定授权

短标记只负责请求对齐，不自动合并含义；译文复用依据 Agent 发布的 `equivalence`。
它明确列出已译来源 `fromUnitId` 和待译目标 `toUnitIds`，并将双方纳入适用范围和已读证据。
例如，同一菜单标签在相同含义下的重复出现，可以形成一次有依据的等义决定。
同名人物与道具、不同说话人和不同义项继续按各自场景处理。

应用复用时，主程序核对来源的已接受译文、决定修订、目标当前修订、人工锁和原生保护规则。
目标保留自己的 ID、上下文、备注和校对责任，接受状态记录所用语义决定。

## 4. 校对提交审阅范围、问题与必要修改

模型的差分校对仍使用同一分段协议，只返回实际需要修改的完整文字：

```text
[u1]
完整改文。
[完成]
```

`[完成]` 独占一行，确认本次请求的冻结目标已全部审阅，不再让模型抄写全部 `reviewed` 编号。
没有修改时只返回完成标记；空回复不算通过。未明确完成时仅保留明确修改或报告疑点的条目，
不能确认省略的文字已审阅。准确自然的条目保持原样。
疑点在 `[附加信息]` JSON 中使用 `questions:[["u2","needs_evidence或source_ambiguity","说明"]]`。
必要备注使用 `remarks`。未附修改说明时，主程序明确记录“模型未附修改说明”，不编造纠错依据。
主程序恢复稳定 ID 和捕获的修订，转换为内部 `pinhao-review-1` 候选，再执行原有 D2 收尾与 CAS 提交。
模型不重写准确的整批译文，也不承担工程版本管理。

输出截断、断流或用户暂停时，已经闭合的明确改文可以进入现有候选接受检查。重复标记、
缺控制符、缺关联伙伴、待补证据或已变化的人工修订不能据此通过。未闭合的末条和省略条目
不算已审阅；恢复时只补未确认目标，保留有效改文作为只读参考，正式提交仍等待本轮收尾。

| 问题 | 保存结果 |
| --- | --- |
| `correction` / `fixed` | 记录纠错依据与完整修改候选，统一收尾后提交 |
| `needs_evidence` / `open` | 保留当前译文，将具体疑点列为待补证据 |
| `source_ambiguity` / `retained` | 记录原作歧义及保留依据 |

零修改审阅同样有效。译文与备注保持原样时，文字 revision 保持原值，审阅戳和问题记录独立更新。
完整关联组、控制符、当前修订和人工锁统一参与接受检查；重复提交使用同一审阅身份处理。

校对轮次冻结已有译文及相关术语。场景审阅先保存候选，正式文字保持当前版本。
场景完成后按其有效成果在本地重算独立译名票数；安全的独立姓名、资料字段按既有规则统一，
不根据中文子串替换对白，也不把一个字段的多次引用算成多票。人物关联或术语出现本身不触发再次审阅。
仍有真实分歧或明确待补证据时，只把相关完整文字列为修改目标，其他场景和人物材料按需只读。
没有残留问题直接定稿；原作歧义保留依据，不为消除原作歧义反复买请求。
候选确实冲突时交回同一轮次核对证据；仍待查的含义保留当前译文并记录问题。
收尾完成后统一核对控制符、关联显示、术语和人工修订，再提交正式译文。
人工改文或译名变化只更新相关范围；其余有效候选继续使用。

## 5. 已返回、已保存和已接受各有记录

主程序在收到完整记录时保存候选，并在正式接受前核对稳定 ID、关联组、控制符、术语、
依赖版本和当前修订。正常回复、流式记录、异常后的候选恢复使用同一套规则。
译名差异作为有依据的校对提示，不用固定词表机械否决有效正文。
完整合法候选可以直接进入本地恢复；冲突关联组进入定向返修，其他已通过记录保留。

任务依赖包含实际补读、搜索回执、当前译文和提示协议版本。
暂停、取消和重开沿用持久检查点，重新核对仍然有效的成果，再处理剩余文字。
分段格式版本与语义依赖版本分开，后者仍为 `pinhao-text-1`；换回复格式不清空已有有效候选。
翻译流中只有被下个标记明确结束的块才能提前保存，正常结束后才接纳最后一块。
后续发现重复标记会撤销该目标的本次候选，独立合法块保留。校对不以流式片段确认整批完成。
使用当前译文生成成品后，未提交的校对轮次和有效候选仍可继续，不因成品已生成而重新购买已完成的审阅。
人工修改发生在请求期间时，提交按修订检查保留用户新内容，并重新安排受影响项。

接口异常分别保存类别、结束原因、请求编号、耗时、已返回记录和供应商原始 usage。
限流与暂态故障使用同连接共享冷却，取消可以中断等待；截断和缺项按剩余目标继续处理。
模型服务已经执行、响应传输中断的情况按已有回执记录，供应商提供的消耗数据随请求保存。

模型请求沿用供应商的输出配置，程序移除了固定的小额输出上限。截断后的有效完整记录保留，
没有新增有效结果的同一截断请求等待调整模型配置后继续。正文与推理分别统计。
实际请求、传输回包及解析结果保存在项目私有请求目录；数据库保存引用，工作包与成品沿用各自的文件清单。

文字工作包继续使用稳定 ID、源文、上下文和基线进行交换。
其可编辑文件与内部 API 差分校对协议分别适配，外部工具可以沿用现有工作包入口。
格式说明见 [文字工作包](TEXT_PACKAGE.md)。

## 6. 已验证文字继续制作，成品携带内容证明

默认流程允许已通过回写检查的文字继续翻译、校对和生成独立成品。
剩余资源保留原文与覆盖记录，用户可以继续提取和补漏；严格流程由“遇到局部失败时暂停”设置控制。
文字完成百分比与资源覆盖分别展示，待补语义证据也有独立问题记录。

字体、图片、补充文字与辅助组件处理完成后，主程序为最终托管文件生成内容清单。
构建复用和分享导出核对该清单；文件内容变化后重新建立对应证明，现有修改副本保留。
存档、运行日志等可变内容按独立规则处理。清理旧成品时再次核对托管内容，保留人工修改。

MV/MZ 游玩辅助的重复安装保持成品文件内容稳定。RGSS 辅助保存原脚本备份，
支持原子安装、中断恢复和卸载还原，冲突保留明确的处理记录。
具体辅助能力见 [游玩辅助](PLAY_ASSIST.md)。

原生回写、组合改文和资源引用属于结构检查。进程与窗口信号属于启动观察。
中文画面、字体布局、对话分支、游玩辅助、保存和读档属于实际游玩检查。
每层保存自己的结果；接入的运行验证器可以返回相应验收记录，成品展示实际已经取得的证据。

最终构建失败时，错误阶段、文字修订、绑定和实际工件进入技术返修包。
技术 Agent 据此定位并修复回写或组装问题，已接受译文作为已有成果继续保留。
